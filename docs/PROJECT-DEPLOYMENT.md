# Deploying a project with Comote

Comote can deploy a Node application as a static site or a long-running service. Every application receives an isolated Linux user, persistent storage, HTTPS, health checks, immutable releases, and application rollback.

The simplest workflow is conversational: in the project's Comote task, ask Codex to configure production. Examples:

- `Configure this app for production with SQLite, migrations, and a /health endpoint.`
- `Use PostgreSQL in production, run the Prisma migration before activation, and require SESSION_SECRET.`
- `Use MySQL and Redis, then configure a health check.`

Codex should create and commit `comote.deploy.json`. Comote reads that file from the clean canonical branch.

## Configuration file

```json
{
  "version": 1,
  "runtime": "node",
  "install": ["npm", "ci", "--include=dev", "--no-audit", "--no-fund"],
  "build": ["npm", "run", "build"],
  "start": ["npm", "start"],
  "migrate": ["npm", "run", "migrate"],
  "healthPath": "/health",
  "healthTimeoutSeconds": 60,
  "services": {
    "sqlite": true,
    "postgres": false,
    "mysql": false,
    "redis": false
  },
  "requiredSecrets": ["SESSION_SECRET"],
  "persistentPaths": ["uploads", ".next/cache"],
  "env": {
    "PUBLIC_APP_NAME": "Example"
  }
}
```

Choose at most one primary database: `sqlite`, `postgres`, or `mysql`. Redis can be enabled alongside any primary database. Static sites use `staticDir` instead of `start`, for example `"staticDir": "dist"`.

Command fields are JSON arrays, not shell strings. This preserves exact arguments and avoids shell interpolation. `install` defaults to `npm ci`, `build` and `start` default to matching package scripts, and all commands execute as the application's locked Linux user.

## Injected environment

Every service receives `HOST=127.0.0.1`, `PORT`, `NODE_ENV=production`, `COMOTE_RELEASE_ID`, `COMOTE_DATA_DIR`, and `COMOTE_CACHE_DIR`. Store uploads and other durable files below `COMOTE_DATA_DIR`; release directories are replaceable and read-only at runtime. Use `persistentPaths` for frameworks that must write to a project-relative path, such as uploads or `.next/cache`; Comote links those paths to durable shared storage.

Depending on the selected services, Comote also supplies:

- SQLite: `DATABASE_URL` and `SQLITE_PATH`, pointing to the persistent `app.db`.
- PostgreSQL: `DATABASE_URL`, `POSTGRES_URL`, and standard `PG*` variables.
- MySQL: `DATABASE_URL`, `MYSQL_URL`, and standard `MYSQL_*` variables.
- Redis: `REDIS_URL`, `REDIS_HOST`, `REDIS_PORT`, and `REDIS_PASSWORD`.

Database passwords are generated by Comote and never shown in the UI. User secrets are saved in **Changes → Production → Environment secrets** as `NAME=value`; the API returns only their names. Do not commit secrets to Git or put them in the public `env` object.

## Release safety

The deployment order is install, build, resource provisioning, pre-migration backup, migration, service activation, health check, and Nginx activation. A failed service or health check restores the previous application release. Database migrations are not automatically reversed; write backward-compatible migrations and use the pre-migration or daily database backup for an intentional database restore.

SQLite and persistent files are captured while application services are stopped during the daily backup. PostgreSQL and MySQL also receive native logical dumps. Redis uses append-only persistence and is stopped briefly for a consistent filesystem snapshot.
